# QQQ 温度计：治理边界、审批矩阵与发布门槛

独立验证和“防伪测试”边界以 [`QQQ_VERIFICATION_GOVERNANCE_BASELINE.md`](QQQ_VERIFICATION_GOVERNANCE_BASELINE.md) 为准；本文件继续负责产品权限、策略审批、paper 运行和发布分级。两者共同构成 QQQ 项目的治理基线。

## 1. 核心边界

```text
研究结论 ≠ 产品策略
温度计展示 ≠ 新策略
目标权重 ≠ 真实订单
盘中观察 ≠ 收盘确认
历史回测 ≠ 未来承诺
```

产品第一阶段只允许“数据 → 指标 → v10 状态 → 目标权重 → paper ledger → 展示”。任何越过 paper ledger 的动作都不在默认范围内。

本项目最终按个人使用模式治理，不追求生产级平台能力。个人模式的范围、延期模块和日常操作见 [`PERSONAL_USE_GOVERNANCE.md`](PERSONAL_USE_GOVERNANCE.md)；worktree 的清洁、checkpoint、artifact 备份和回滚见 [`WORKTREE_RESTORE_PROTOCOL.md`](WORKTREE_RESTORE_PROTOCOL.md)。

## 2. 策略治理

### 策略真相

- v10 的规则、参数、资产集合、执行时点和成本必须只有一个机器可读来源。
- `final_regime_ensemble` 等旧版本只作为 baseline/legacy 展示和对照，不能被页面或 API 静默替换。
- 每次策略变化创建新的版本号和配置 hash；旧版本只读。
- 前端只能请求“当前已批准版本”，不能提交阈值、权重或状态覆盖。

### 不允许的优化方式

- 以最近一年、单个危机、单个账户截图或年度胜率最大化调参。
- 在看到验证区间结果之后再选择指标、阈值或资产。
- 以“每年都跑赢 QQQ”作为硬性承诺。
- 为了降低最大回撤而无条件加入 VXX、SVXY、QLD、杠杆、期权或复杂指标。
- 将指标数量越多等同于模型越可靠。

### 研究要求

新版本至少记录：先验假设、经济解释、固定参数、训练/选择区间、验证区间、未参与选择的阶段、失败年份、成本压力测试、与 QQQ 的差异和数据局限。

## 3. 数据治理

- 原始数据不可变；标准化数据可重建；指标、状态和目标权重可由 manifest 复现。
- 所有数据必须标识来源、抓取时间、时区、交易日、价格调整口径和代理关系。
- 盘中数据只生成 `PROVISIONAL`；收盘后完成数据质量检查才可生成 `CONFIRMED`。
- 缺失、过期、跨源价格差异和供应商变更必须生成质量事件；不能静默向前填充。
- VIX/VIX3M 仅作为信号；VXX/SVXY 等 ETF 的历史价格和衰减风险必须单独处理。
- 原始行情、账户持仓、聊天记录或截图不能无必要地上传到外部服务；若需要外部数据，先确认范围、权限和保留期限。

## 4. 交易与账户治理

### 当前明确禁止

- 真实券商 API、API key、账户登录、下单、撤单、转账、借贷或自动再平衡。
- 以页面按钮触发真实订单。
- 在日志、数据库、Git 或报告中保存券商密钥或完整账户标识。

### 未来若要进入实盘，必须单独审批

至少需要：独立 broker adapter、只读/交易权限分离、最小权限密钥管理、人工确认或 kill switch、订单幂等、成交回报对账、异常停止、审计日志、回滚和连续 paper shadow 证据。没有这些条件，系统只能保持 paper 模式。

## 5. 前端与文案治理

- 温度、趋势、agreement、红黄绿状态必须同时提供文字、数值/证据和更新时间。
- `Signal Agreement` 表示多个已定义信号的方向一致程度，不表示收益概率、预测胜率或暴跌概率。
- “可能继续上涨/下跌”只能写成条件化的历史或规则解释，例如“若条件 A/B 持续满足，策略会保持某状态”。
- 页面不能暗示“策略保证低于 QQQ 回撤”“保证跑赢 QQQ”或“能够提前知道暴跌”。
- 参考第三方网站只借鉴信息层次和交互模式；不复制其代码、品牌、文案、素材、图标或独特视觉设计。
- 账户持仓页面默认最小化显示敏感信息，开发截图和演示数据使用脱敏或合成数据。

## 6. Codex 工作治理

### 每次任务开始前

1. 读取根 `AGENTS.md` 和目标目录局部规则。
2. 查看 `git status`、目标文件和相关调用关系。
3. 明确本次唯一模块、允许修改的路径和不变项。
4. 检查是否触及策略、数据、权限、依赖或外部系统。

### 每次任务中

- 只做当前模块；用 `apply_patch` 修改；保留用户已有脏文件。
- 不使用破坏性 Git 命令，不批量格式化，不顺手重构。
- 先写确定性测试，再实现；不能测试的规则先转为待确认的合同。
- 不擅自安装插件、依赖或连接外部系统。

### 每次任务结束时

- 报告修改文件、测试证据、数据/策略结果是否变化、未覆盖风险和回滚路径。
- 当前模块未通过就停止，不自动进入下一模块。
- 文档和报告必须明确“研究结果”“paper 结果”“实时观察”三者的区别。

## 7. 变更审批矩阵

| 变更 | 默认处理 | 是否需要用户明确批准 |
|---|---|---|
| 文档、测试、目录占位 | 本地执行 | 通常不需要，完成后报告 |
| 页面文字、布局、无业务语义的样式 | 本地执行 | 通常不需要；不得改变风险语义 |
| 新指标、阈值、资产、权重或执行时点 | 新版本研究 | 需要 |
| API schema、数据库表、迁移 | 单独模块 | 需要审阅；破坏性迁移必须明确批准 |
| 新数据供应商或价格口径 | 数据审计 | 需要 |
| 新依赖、定时任务、外部服务 | 变更评估 | 需要 |
| 真实券商接入、密钥、订单 | 禁止默认执行 | 必须单独批准并完成实盘治理 |
| 私有部署 | 发布门槛 | 需要 |
| 公网部署或对外分享 | 超出默认范围 | 必须单独批准 |

## 8. 发布分级与回滚

### L0：文档/目录

只验证文件内容、链接、目录和 Git 差异。

### L1：本地只读原型

使用固定 fixture；无外部写入；可展示加载、空、错误、陈旧和确认状态。

### L2：历史回放

通过无前视测试、逐日回放、基准对账和成本压力测试；输出可复现报告。

### L3：paper shadow

至少连续 20 个交易日，记录每日信号、目标、模拟执行、成本、持仓、NAV、数据质量和异常；发现时点或数据问题时停止晋级。

### L4：私有使用

完成访问控制、密钥不入库、备份恢复、运行监控、版本回滚和用户确认。仍然不等于允许实盘下单。

回滚优先使用“切回上一份已批准的策略版本/前端版本/数据 manifest”，不删除历史产物，不覆盖账本。

## 9. 需要用户确认的事项

在进入 M01 之后，用户需要确认：

1. v10 是否作为产品默认候选，还是仅作为研究展示；
2. 目标数据源、价格口径、更新频率和允许的代理数据；
3. paper ledger 的初始资金、成本、滑点和再平衡时点；
4. 私有访问方式和数据保留范围；
5. 是否允许后续建立独立的前端应用；
6. 任何真实交易需求（如果未来出现）是否另开任务和独立权限。
